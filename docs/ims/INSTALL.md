# ZIP A — controlled deployment
Base: commit 9c74d892a048da9df64e690539293b28cf17751e. Patch contains only listed files, not a replacement repository. Back up existing database using hosting controls and verify restoration arrangements before migration. Use a clean branch and verify changes. No new npm dependencies. Run node scripts/migrate-ims.js against the configured database before deploying the new server code (the script uses existing DB environment variables). Do NOT run db:setup on an existing installation: it can reset the administrator password. For managed hosting with remote DB access disabled, run migration on the host or execute db/migrations/003_ims_core.sql in its database management tool. Migration is additive and repeatable; it does not delete existing rows. MySQL max_allowed_packet must accommodate uploads (at least 8 MiB recommended). Existing session/role and APP_ROLE configuration remain required.

Smoke test: sign in, check live dashboard, open existing partner and work-order views, create a harmless TXT document, submit for review, approve with note and future review date, download and compare SHA-256, upload new revision, reject it and verify original approved version remains. Verify a dispatcher/viewer receives 403 on IMS APIs; unauthenticated access receives 401. Verify logout and sign-in again. Do not send real dispatch emails during testing. Test backups on a separate database. No live environment validation has been performed here.

Rollback: revert the patch commit and redeploy prior app; additive IMS tables can remain in place. Do not drop tables containing evidence. If migration fails, inspect the error and rerun after remediation; avoid using the new document interface before migration succeeds.
